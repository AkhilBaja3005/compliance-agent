# Optional SDK infrastructure adapters

The default composition imports only the memory adapters. `S3BlobStore` and `SqsJobQueue` are optional modules, implementing `BlobStore` and `JobQueue`. Their constructors accept already supplied SDK clients and existing-resource identifiers. They never construct clients, inspect the environment, resolve credentials, or provision resources. An authorized caller would explicitly inject adapter instances through `createProduct(catalog, {blobs, queue, clock})`. No such clients were supplied or invoked during repository creation.

AWS's official [S3 JavaScript v3 examples](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/javascript_s3_code_examples.html) document client `send`, `PutObjectCommand`, `GetObjectCommand`, `DeleteObjectCommand`, and response-body `transformToString()`. The adapter uses these to store versioned JSON envelopes of synthetic source records, retrieve them, and delete them. Keys are validated and prefixed by tenant. It sets JSON content type, requests AES256 server-side encryption, and includes expiration metadata. The service's [PutObject reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html) describes these request semantics; [GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html) describes content-length responses. Reads reject missing/oversized bodies and return undefined for `NoSuchKey` or expired envelopes.

AWS's official [SQS JavaScript v3 examples](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/javascript_sqs_code_examples.html) document `SendMessageCommand`, `ReceiveMessageCommand`, `ChangeMessageVisibilityCommand`, and `DeleteMessageCommand`. The adapter serializes no credentials or face data: only a validated versioned tenant/job reference. It receives one message with a 120-second visibility lease and one-second long poll, changes visibility for delayed retry, and acknowledges by receipt handle. Use an existing **standard** queue; FIFO group/deduplication fields are intentionally absent. Queue bodies are validated again by the worker.

The SDK's official [AbortController documentation](https://github.com/aws/aws-sdk-js-v3#abort-controller) documents the `abortSignal` send option. `withDeadline` supplies that signal and races the entire operation against a five-second timeout, clearing its timer in all outcomes. An abort is requested on timeout; the caller deadline also covers body decoding. This does not prove a remote write was cancelled; idempotent keys and ingestion markers handle ambiguous outcomes. Provider details are redacted into structured errors. Timeouts, throttling, and transient HTTP failures are retryable; configuration/permission failures are terminal.

Existing resource policy must restrict access to the intended bucket prefix and queue. Application expiration metadata is not an S3 lifecycle rule. The application sweep explicitly deletes expired objects. For an actual adapter deployment, existing storage must also have appropriate lifecycle handling for interrupted/uncommitted writes and, if versioned, noncurrent versions; existing queue message retention must be bounded. This repository supplies no policies, provisioning, bucket operations, or queue creation. In-memory data disappears when the application object is discarded.

`package.json` declares genuine modular AWS SDK v3 packages with minimum-version ranges, not a lockfile. Official documentation supports the API shapes; the minimum versions, dependency resolution, TypeScript compatibility, body-stream timeout cancellation details, IAM settings, queue settings, and runtime integration have not been verified by execution. Current generated API-reference pages yielded minimal text; the substantive AWS developer-guide examples and official SDK README were used instead. The SDK-shaped stub tests are authored only and do not establish SDK or service compatibility. Neither adapter collects images or computes biometrics.
