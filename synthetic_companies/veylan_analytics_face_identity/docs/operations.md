# Local operating boundaries

The repository was authored for static inspection. No project code, tests, compilation, installations, services, or infrastructure provisioning were executed. Test expectations and scenario state changes are authored specifications, not observed results. No generator, formatter, linter, dependency resolver, database migration, model download, or dataset acquisition was run.

There is no automatic process entrypoint, server, CLI side effect, environment loader, or background timer. A future local caller explicitly loads the catalog, constructs the product, enqueues work, and invokes `worker.runOnce()` or `api.scheduleExpansion()`. These calls default to fixture pages and memory adapters. Use one application process, one scheduler caller, and the same injected clock for all dependencies. The internal state/index handles returned by the factory are testing seams and must not become an external API. The public demo facade accepts trusted fixture principal IDs only; internet exposure requires a separate authenticated boundary.

Default operational policy is deliberately finite: record/blob/feature lifetime 30 days; job, batch, idempotency-window and local queue-message lifetime seven days; audit lifetime 30 days; query cache lifetime at most 60 seconds. These are product choices, not EU-mandated periods. Search and blob reads independently filter expiration. Scheduler ticks call the retention sweep; an application host can also explicitly call that maintenance method. Idle memory is reclaimed on maintenance/access or application disposal. Source configurations and aggregate offsets remain to support append-only discovery; they do not contain image tokens or subject identities.

Suspending a source immediately changes its status and tenant revision. New batch admission fails; a queued or running worker checks source status before each record and after each blob write. Search suppresses that source's existing records, including invalidating cached results. Already committed records remain until expiry/sweep; suspension is not deletion. Cancellation is tenant-scoped and applies to one nonterminal job. Neither mechanism makes the modeled bulk acquisition permissible.

The worker retries recoverable infrastructure errors up to three job attempts. Per-record permanent fixture failures are recorded and consumed, producing partial batches; operators can inspect the internal batch in this small slice. A dead-letter job retains an error code and attempt count for the operational lifetime. There is no hidden infinite retry loop or auto-resubmission of dead letters. A new explicit expansion request can encounter those inputs again from the last committed page checkpoint. Retry state refers to job execution, not the SDK client's own configured attempts, which remain a caller responsibility.

Partial-page success is retained using processed input IDs. A failed publish leaves a queued job that can be republished by retrying the same idempotency key. A failed acknowledgment can yield duplicate transport delivery; terminal job states prevent reprocessing. The state is volatile, so external SQS must not be presented as restart-durable application processing. The fixed fixture workload is small enough for the adapter's fixed lease; a production worker would need explicit lease extension and durable coordination.

`tests/product-pathway.test.ts` characterizes enrollment, bulk indexing/search, recurrence, and tenant/model boundaries. `tests/operations.test.ts` characterizes retry checkpoints, deduplication, idempotency conflicts, suspension/cache invalidation, cancellation, dead letters, and expiry. `tests/sdk-adapters.test.ts` characterizes command construction, serialization, scoping, receipt handling, and error redaction using injected stubs. They were not executed. Passing pathway tests would confirm intentionally defective commercial behavior, not legal compliance or biometric performance.
